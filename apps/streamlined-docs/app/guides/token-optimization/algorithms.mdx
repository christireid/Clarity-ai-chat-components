# Token Optimization Algorithms

A comprehensive technical guide to the algorithms powering Clarity Chat's token optimization system. This guide covers 8 core algorithms with detailed explanations, benchmarks, and tradeoff analysis.

## Overview

Token optimization algorithms reduce API costs by 50-70% (up to 90% with provider caching) through intelligent text processing. Each algorithm serves a specific purpose and excels in different scenarios.

### Algorithm Categories

| Category | Algorithms | Primary Use Case | Token Reduction |
|----------|-----------|------------------|-----------------|
| **Text Compression** | LLMLingua, Extractive, Adaptive | Reduce prompt size while preserving meaning | 40-80% |
| **Semantic Chunking** | Text Chunker, Sliding Window | Break long documents into optimal chunks | Context control |
| **Context Management** | Budget Monitor, History Truncation | Stay within model context limits | Prevent errors |
| **Provider Caching** | Anthropic, OpenAI, Google | Reuse static content across requests | 50-90% on cached |

## Text Compression Algorithms

### 1. LLMLingua Compression

**Algorithm Type**: Statistical token pruning
**Complexity**: O(n log n) where n = token count
**Best For**: Prose text, instructions, prompts

#### How It Works

LLMLingua removes low-information tokens while preserving semantic meaning through a 5-step process:

```typescript
// Algorithm Steps:
1. Tokenization: Split text into words and punctuation
2. TF-IDF Scoring: Calculate importance using term frequency × inverse document frequency
3. Position Weighting: Boost tokens at start/end (1.5-2.0x multiplier)
4. Instruction Detection: Preserve tokens near keywords like "must", "important"
5. Token Selection: Keep top N tokens by importance score
```

#### Implementation Details

```typescript
import { LLMLinguaCompressor } from '@clarity-chat/token-optimization'

const compressor = new LLMLinguaCompressor({
  preserveFirst: 10,        // Keep first 10 tokens
  preserveLast: 5,          // Keep last 5 tokens
  preserveInstructions: true, // Boost instruction markers
  preserveCode: true,       // Keep code blocks intact
  minQuality: 0.7,         // Minimum quality threshold
  maxRecursionDepth: 5     // Max quality retry attempts
})

// Compress to 50% of original tokens (2x compression)
const result = await compressor.compress(text, 0.5)

console.log('Compression:', result.compressionRatio)
console.log('Token reduction:', result.tokenReductionRatio)
console.log('Quality:', result.quality.overallQuality)
```

#### Scoring Formula

For each token, the importance score is calculated as:

```
importance = (TF × IDF × positionWeight) - penalties + bonuses

where:
  TF = frequency of term in document
  IDF = log(numSentences / sentencesContainingTerm) + 1
  positionWeight = {
    2.0 if position < 10% of document
    1.6 if position > 90% of document
    1.0 otherwise
  }
  penalties = {
    0.9 if stopWord (reduce by 90%)
    0.5 if punctuation
  }
  bonuses = {
    3.0x if near instruction markers
    preserve if in code block
  }
```

| 2000 tokens | 0.3 (3.3x) | 600 tokens | 0.73 | 48ms |

**Key Metrics:**
- **Semantic Similarity**: Cosine similarity of term vectors (0.8-0.95 typical)
- **Key Term Retention**: Percentage of important terms preserved (0.7-0.95)
- **Instruction Retention**: Percentage of instruction markers kept (0.85-1.0)

#### Tradeoffs

**Strengths:**
- ✅ High compression ratios (2-20x) while maintaining readability
- ✅ Preserves semantic meaning through TF-IDF scoring
- ✅ Automatic instruction and code preservation
- ✅ Quality-aware with recursive retry logic

**Weaknesses:**
- ❌ Can break sentence grammar at very high compression (>5x)
- ❌ Slower than extractive for very long documents (>10k tokens)
- ❌ May remove connecting words that aid human readability
- ❌ Less effective on highly technical or domain-specific text

**When to Use:**

- System prompts with natural language
- Conversational context where token-level precision matters
- When you need 2-5x compression with good quality

**When to Avoid:**
- Structured data (JSON, XML, YAML)
- Pure code files
- Legal/medical text requiring exact wording
- Short text (<100 tokens)

### 2. Extractive Compression

**Algorithm Type**: Sentence extraction and ranking
**Complexity**: O(n²) where n = sentence count
**Best For**: Long documents, articles, technical documentation

#### How It Works

Extracts the most important sentences while preserving grammatical coherence:

```typescript
// Algorithm Steps:
1. Sentence Splitting: Break text on sentence boundaries
2. Feature Extraction: Extract entities, key phrases, positions
3. TF-IDF Calculation: Score terms across sentences (documents)
4. Sentence Scoring: Combine 7 scoring factors with weights
5. Selection: Pick top-scored sentences, sort by original position
```

#### Implementation Details

```typescript
import { ExtractiveCompressor } from '@clarity-chat/token-optimization'

const compressor = new ExtractiveCompressor({
  minSentences: 3,           // Keep at least 3 sentences
  maxSentences: 20,          // Cap at 20 sentences
  preserveFirst: true,       // Always include first sentence
  preserveLast: false,       // Don't always include last
  boostQuestions: true,      // Prioritize questions
  boostInstructions: true,   // Prioritize instructions
  keyPhrases: ['API', 'authentication'], // Custom boost terms
  minSentenceLength: 10      // Minimum chars per sentence
})

// Keep 50% of sentences
const result = compressor.compress(text, 0.5)

console.log('Kept sentences:', result.keptSentences, '/', result.originalSentences)
console.log('Quality:', result.quality.overallQuality)
```

#### Scoring Formula

For each sentence, the importance score combines 7 weighted factors:

```
score = (
  positionScore × 1.5 +
  keyPhraseScore × 2.0 +
  entityScore × 1.0 +
  instructionScore × 2.5 +
  questionScore × 2.0 +
  lengthScore × 0.5 +
  tfIdfScore × 1.5
)

where:
  positionScore = {
    1.0 if first sentence
    0.8 if last sentence
    0.7 if in first 20%
    0.5 otherwise
  }

  keyPhraseScore = min(1.0, matchCount / 3)

  entityScore = min(1.0, entityCount / 5)
  // Entities: capitalized words, URLs, emails, numbers with units, camelCase/snake_case

  instructionScore = 1.0 if contains instruction markers, else 0.0
  // Markers: must, shall, should, important, warning, step, etc.

  questionScore = 1.0 if contains question markers, else 0.0
  // Markers: ?, what, who, where, when, why, how, can you, etc.

  lengthScore = {
    1.0 if 10-30 words (optimal)
    0.7 if 5-50 words (acceptable)
    0.5 otherwise
  }

  tfIdfScore = averageTfIdf(sentence)
  // TF-IDF averaged across all terms in sentence
```

#### Tradeoffs

**Strengths:**
- ✅ Preserves perfect sentence grammar and coherence
- ✅ Fast for very long documents (linear in sentence count)
- ✅ Human-readable output (complete sentences)
- ✅ Excellent for summarization use cases

**Weaknesses:**
- ❌ Lower compression ratios than token-level methods (typically 2-5x vs 2-20x)
- ❌ Can lose nuance within sentences
- ❌ Less effective on short documents (<10 sentences)

**When to Avoid:**

### 3. Adaptive Compression

**Algorithm Type**: Meta-algorithm with content analysis
**Complexity**: O(n) analysis + strategy-specific compression
**Best For**: Unknown content types, mixed content

#### How It Works

Analyzes content and automatically selects the best compression strategy:

```typescript
// Algorithm Steps:
1. Content Analysis: Detect type, length, complexity, features
2. Strategy Scoring: Score each strategy (LLMLingua, Extractive, Hybrid, Minimal)
3. Strategy Selection: Pick highest-scoring strategy
4. Compression: Apply selected strategy with optimized parameters
5. Quality Check: Verify results meet requirements
```

#### Implementation Details

```typescript
import { AdaptiveCompressor } from '@clarity-chat/token-optimization'

const compressor = new AdaptiveCompressor({
  targetRatio: 0.5,           // Target 50% compression
  minQuality: 0.75,           // Minimum acceptable quality
  maxProcessingTime: 5000,    // Max 5 seconds
  preferredStrategy: 'llmlingua', // Prefer LLMLingua if suitable
  debug: true                 // Get strategy reasoning
})

const result = await compressor.compress(text)

console.log('Strategy used:', result.strategyUsed)
console.log('Reason:', result.strategyReason)
console.log('Content type:', result.contentAnalysis.contentType)
console.log('Confidence:', result.contentAnalysis.typeConfidence)
```

#### Content Type Detection

The analyzer examines multiple features to classify content:

```typescript
// Content types and detection criteria:
{
  prose: {
    codePercentage: < 0.3,
    hasStructuredData: false,
    typical: "Natural language text, articles, documentation"
  },

  code: {
    codePercentage: > 0.7,
    codeBlocks: true,
    typical: "Programming code, scripts, functions"
  },

  mixed: {
    codePercentage: 0.3-0.7,
    codeBlocks: true,
    typical: "Technical docs with code examples"
  },

  structured: {
    hasJson: true || hasXml: true,
    typical: "JSON, XML, YAML configuration"
  },

  conversational: {
    hasQuestionAnswerPattern: true,
    typical: "Chat logs, Q&A, dialogue"
  },

  technical: {
    hasSections: true && hasCodeBlocks: true,
    complexity: > 0.6,
    typical: "API docs, technical specifications"
  },

  list: {
    listLines / totalLines: > 0.5,
    typical: "Bullet points, enumerated items"
  }
}
```

#### Strategy Selection Scoring

Each strategy gets a score (0-1) based on content characteristics:

```typescript
// LLMLingua scoring:
baseScore = 0.5
if (contentType === 'prose') score += 0.3
if (contentType === 'mixed') score += 0.2
if (tokens >= 100 && tokens <= 5000) score += 0.2
if (targetRatio < 0.4) score += 0.2 // Aggressive compression
if (hasStructuredData) score -= 0.3
if (contentType === 'code') score -= 0.4

// Extractive scoring:
baseScore = 0.4
if (sentences > 20) score += 0.3
if (contentType === 'prose' || 'technical') score += 0.2
if (targetRatio >= 0.3 && <= 0.7) score += 0.1 // Moderate compression
if (minQuality > 0.8) score += 0.2 // High quality required
if (sentences < 5) score -= 0.3
if (contentType === 'list') score -= 0.2

// Hybrid scoring:
baseScore = 0.3
if (complexity > 0.6) score += 0.3
if (contentType === 'mixed') score += 0.3
if (tokens > 5000) score += 0.2 // Very long documents
if (minQuality > 0.85) score += 0.2 // Very high quality
if (maxProcessingTime < 1000) score -= 0.3 // Time constrained

// Minimal scoring (whitespace only):
baseScore = 0.2
if (tokens < 50) score += 0.4
if (hasStructuredData) score += 0.3
if (contentType === 'code') score += 0.3
if (targetRatio > 0.8) score += 0.2 // Conservative compression
```

**Strengths:**

- ✅ Optimal results across different content types
- ✅ Built-in quality assurance
- ✅ Detailed content analysis for debugging

**Weaknesses:**

**When to Avoid:**
- Performance-critical paths (use direct strategy)
- When you know exactly what strategy works best

## Semantic Chunking Algorithms

### 4. Text Chunker (llm-splitter)

**Algorithm Type**: Greedy paragraph-aware chunking
**Complexity**: O(n) single-pass
**Best For**: RAG systems, document processing, context management

#### How It Works

Splits text into optimally-sized chunks with configurable overlap:

```typescript
// Algorithm Steps:
1. Tokenization: Split on words while preserving whitespace
2. Paragraph Detection: Identify natural paragraph boundaries
3. Greedy Chunking: Fill chunks to maxTokens, respecting paragraphs
4. Overlap Generation: Add overlap tokens from previous chunk
5. Metadata Enrichment: Add position, token counts, paragraph markers
```

#### Implementation Details

```typescript
import { TextChunker, ChunkingStrategy } from '@clarity-chat/token-optimization'

// Predefined strategies
const preciseChunker = TextChunker.precise()     // 256 tokens, 10% overlap
const balancedChunker = TextChunker.balanced()   // 512 tokens, 15% overlap
const contextChunker = TextChunker.context()     // 1024 tokens, 20% overlap

// Custom configuration
const customChunker = new TextChunker({
  maxTokens: 512,
  overlapPercentage: 0.15,
  strategy: ChunkingStrategy.CUSTOM,
  includeTokenCount: true
})

const result = customChunker.chunk(longDocument)

result.chunks.forEach(chunk => {
  console.log(`Chunk ${chunk.index}:`)
  console.log(`  Tokens: ${chunk.tokenCount}`)
  console.log(`  Position: ${chunk.startPosition}-${chunk.endPosition}`)
  console.log(`  New paragraph: ${chunk.metadata.startsNewParagraph}`)
})
```

#### Strategy Presets

```typescript
const STRATEGY_PRESETS = {
  PRECISE: {
    maxTokens: 256,
    overlapPercentage: 0.1,
    // Use for: Precise retrieval, semantic search
    // Characteristics: Many small chunks, minimal overlap
  },

  BALANCED: {
    maxTokens: 512,
    overlapPercentage: 0.15,
    // Use for: General-purpose RAG, most applications
    // Characteristics: Moderate chunks, balanced overlap
  },

  CONTEXT: {
    maxTokens: 1024,
    overlapPercentage: 0.2,
    // Use for: Context preservation, complex documents
    // Characteristics: Large chunks, generous overlap
  }
}
```

#### Overlap Mechanism

```typescript
// Overlap ensures context continuity between chunks:

Chunk 1: [Token 0-512]
Overlap:              [Token 435-512] (15% of 512 = 77 tokens)
Chunk 2:              [Token 435-947]
Overlap:                              [Token 870-947]
Chunk 3:                              [Token 870-1382]

// Benefits:
1. No information loss at chunk boundaries
2. Each chunk has context from previous chunk
3. Allows sliding window processing
4. Improves embedding quality for RAG
```

|--------------|----------|--------|----------|-----------------|
| 5,000 tokens | Precise | 21 | 10% | 25ms |

**Key Metrics:**
- **Overhead Percentage**: Extra tokens from overlapping chunks (10-20%)
- **Chunk Count**: Number of chunks generated
- **Processing Speed**: ~3,000-5,000 tokens/ms (very fast)

#### Tradeoffs

**Strengths:**
- ✅ Extremely fast - single-pass algorithm
- ✅ Paragraph-aware - respects natural boundaries
- ✅ Configurable overlap for context continuity
- ✅ Minimal dependencies (uses lightweight llm-splitter)
- ✅ Rich metadata for downstream processing

**Weaknesses:**
- ❌ Greedy approach may not find globally optimal chunks
- ❌ Overlap creates token duplication (10-20% overhead)
- ❌ May split mid-sentence if paragraph is too long
- ❌ Doesn't understand semantic coherence

**When to Use:**
- RAG (Retrieval-Augmented Generation) systems
- Document indexing for vector databases
- Processing documents too large for context window
- Any text chunking need

**When to Avoid:**
- When semantic coherence is critical (use semantic chunker)
- Very short documents (<500 tokens) - chunking not needed
- When zero overlap is required (use custom splitter)

## Context Window Management

### 5. Budget Monitor & Auto-Trimming

**Algorithm Type**: Sliding window with intelligent truncation
**Complexity**: O(n) where n = message count
**Best For**: Conversational AI, chat applications, staying within limits

#### How It Works

Monitors token usage against model limits and automatically trims when needed:

```typescript
// Algorithm Steps:
1. Model Detection: Get context window limit (e.g., 128K for GPT-4o)
2. Token Counting: Count tokens in all messages
3. Status Calculation: Determine if approaching limits
4. Threshold Checks: Warn at 80%, critical at 95%
5. Auto-Trim: Remove oldest messages if enabled (preserve system prompt)
```

#### Implementation Details

```typescript
import {
  useTokenBudgetTracking,
  createModelBudgetMonitor,
  getStatusColor,
  formatTokenUsage
} from '@clarity-chat/token-optimization'

// Create monitor for specific model
const budgetConfig = createModelBudgetMonitor('gpt-4o', {
  warningThreshold: 0.8,      // Warn at 80%
  criticalThreshold: 0.95,    // Critical at 95%
  autoTrim: true,             // Auto-remove old messages
  onWarning: (usage) => {
    console.log('Warning:', usage.utilizationPercent)
  },
  onCritical: (usage) => {
    showNotification('Token budget critical!')
  },
  onAutoTrim: (result) => {
    console.log(`Trimmed ${result.tokensRemoved} tokens`)
  }
})

// Use in React component
const { usage, isWarning, isCritical, updateMessages } = useTokenBudgetTracking(budgetConfig)

// Update when messages change
useEffect(() => {
  updateMessages(messages)
}, [messages])

// Display status
<TokenBar
  value={usage.utilizationPercent}
  color={getStatusColor(usage.status)}
/>
<span>{formatTokenUsage(usage)}</span>
```

#### Auto-Trim Algorithm

When auto-trim is enabled and critical threshold is reached:

```typescript
// Trimming priority (from most to least preserved):
1. System messages - NEVER trim (critical instructions)
2. Latest N user+assistant pairs (conversation context)
3. Older messages - trim oldest first until under threshold

// Example:

  { role: 'system', content: 'You are a helpful assistant' }, // PRESERVED
  { role: 'user', content: 'Old question 1' },                 // TRIMMED
  { role: 'assistant', content: 'Old answer 1' },              // TRIMMED
  { role: 'user', content: 'Old question 2' },                 // TRIMMED
  { role: 'assistant', content: 'Old answer 2' },              // TRIMMED
  { role: 'user', content: 'Recent question' },                // PRESERVED
  { role: 'assistant', content: 'Recent answer' },             // PRESERVED
  { role: 'user', content: 'Current question' }                // PRESERVED
]

// After auto-trim:

  { role: 'system', content: 'You are a helpful assistant' },
  { role: 'user', content: 'Recent question' },
  { role: 'assistant', content: 'Recent answer' },
```

## Message History Truncation Strategies

### 6. Sliding Window Truncation

**Algorithm Type**: Fixed-size window with optional summarization
**Complexity**: O(n) where n = message count
**Best For**: Chat applications, conversational AI

#### How It Works

Maintains a sliding window of recent messages while optionally summarizing older context:

```typescript
// Three truncation strategies:

1. Simple Sliding Window:
   - Keep last N messages
   - Discard everything older
   - Fast but loses history

2. Summarization:
   - Keep last N messages
   - Summarize older messages into context
   - Preserves information, costs tokens

3. Hybrid:
   - Keep last N messages
   - Keep system prompts
   - Summarize middle messages
   - Best balance
```

#### Implementation Patterns

```typescript
// Pattern 1: Simple Sliding Window
function simpleTruncate(messages: Message[], maxMessages: number): Message[] {
  return messages.slice(-maxMessages)
}

// Pattern 2: With System Prompt Preservation
function truncatePreservingSystem(messages: Message[], maxMessages: number): Message[] {
  const systemMessages = messages.filter(m => m.role === 'system')
  const otherMessages = messages.filter(m => m.role !== 'system')

  return [
    ...systemMessages,  // Always keep system prompts
    ...otherMessages.slice(-(maxMessages - systemMessages.length))
  ]
}

// Pattern 3: With Summarization
async function truncateWithSummary(
  messages: Message[],
  windowSize: number,
  summaryTokenLimit: number
): Promise<Message[]> {
  if (messages.length <= windowSize) {
    return messages
  }

  const systemMessages = messages.filter(m => m.role === 'system')
  const conversationMessages = messages.filter(m => m.role !== 'system')

  // Messages to summarize
  const toSummarize = conversationMessages.slice(0, -windowSize)

  // Recent messages to keep
  const recentMessages = conversationMessages.slice(-windowSize)

  // Generate summary
  const summary = await summarizeMessages(toSummarize, summaryTokenLimit)

  return [
    ...systemMessages,
    { role: 'system', content: `Previous conversation summary: ${summary}` },
    ...recentMessages
  ]
}

// Pattern 4: Token-Based Window (more precise)
async function truncateByTokens(
  messages: Message[],
  maxTokens: number
): Promise<Message[]> {
  const result: Message[] = []
  let tokenCount = 0

  // Iterate from newest to oldest
  for (let i = messages.length - 1; i >= 0; i--) {
    const message = messages[i]
    const messageTokens = countTokens(message.content)

    if (tokenCount + messageTokens <= maxTokens) {
      result.unshift(message)
      tokenCount += messageTokens
    } else if (message.role === 'system') {
      // Always include system messages, even if over budget
      result.unshift(message)
      tokenCount += messageTokens
    } else {
      break
    }
  }

  return result
}
```

### 7. Anthropic Prompt Caching

**Algorithm Type**: Explicit cache breakpoints
**Complexity**: O(1) API integration
**Best For**: Repeated system prompts, few-shot examples, large context

#### How It Works

Marks specific content for caching via cache_control breakpoints:

```typescript
// Algorithm Steps:
1. Content Analysis: Identify static vs dynamic content

4. API Call: Send formatted messages to Anthropic

```

## Best Practices

### 1. Combine Multiple Strategies

The best results come from layering optimizations:

```typescript
// Production-ready optimization stack:

1. Provider Caching (90% on static content)
   ↓
2. Text Compression (50-70% on dynamic content)
   ↓
3. Budget Monitoring (prevent overages)
   ↓
4. Smart Chunking (for large documents)

// Example:
const optimizedRequest = async (userQuery: string) => {
  // Step 1: Apply provider caching to system prompt
  const cachedMessages = await anthropicCache([
    { role: 'system', content: STATIC_SYSTEM_PROMPT }
  ])

  // Step 2: Compress user query
  const compressed = await compressAdaptively(userQuery, 0.5)

  // Step 3: Add to messages
  const messages = [
    ...cachedMessages.messages,
    { role: 'user', content: compressed }
  ]

  // Step 4: Monitor budget
  updateMessages(messages)
  if (isCritical) {
    showWarning('Approaching token limit')
  }

  // Step 5: Send to API
  return await claude.messages.create({ messages })
}
```

```typescript
const result = await compressor.compress(text, targetRatio)
```

### 5. Handle Edge Cases

```typescript
// Always handle edge cases gracefully:

const safeCompress = async (text: string, targetRatio: number) => {
  // Edge case 1: Empty or whitespace-only text
  if (!text || text.trim().length === 0) {
    return text
  }

  // Edge case 2: Text already below target
  const currentTokens = countTokens(text)
  if (currentTokens < MIN_COMPRESSION_TOKENS) {
    return text // Don't compress very short text
  }

  // Edge case 3: Compression fails or degrades quality too much
  try {
    const result = await compressor.compress(text, targetRatio)

    if (result.quality.overallQuality < MIN_QUALITY) {
      console.warn('Quality too low, using original text')
      return text
    }

    return result.compressed
  } catch (error) {
    console.error('Compression failed:', error)
    return text // Fallback to original
  }
}
```
